# Runtime memory envelope evidence

This document records the 2026-08-25 local production-shaped acceptance run.
The machine-readable source is `runtime-memory-production.json`, generated by
`scripts/runtime-memory-suite.sh`; CI publishes the same file as a 30-day
artifact. The checked-in comparison reference is
`tests/fixtures/runtime-memory-pre-change-baseline.json`.

## What was confirmed

The 2026-08-22 incident reached about 4.0 GiB anonymous RSS. The previously
confirmed process-lifetime Bluesky collector ownership bug is owned and fixed by
`bound-bluesky-collector-retention`. Its reused churn scenario reached the
configured key/waiter bounds and returned active keys, waiters, retained
identifier bytes, and completed-result owners to zero. The total-process run
therefore attributes **zero settled bytes** to those collector maps; it does not
claim that the old collector bug explained the whole incident.

The candidate run used 10,000 deterministic events and the production cache
capacities (50,000 users, 40,000 posts, and 20,000 negative posts). It covered
live ingestion, replay, genuine SQLite `BEGIN IMMEDIATE` contention, cleanup,
and VACUUM. Every cache filled, evicted, and then cleared. The two fully warmed
samples were:

| Measurement | First warmed | After bounded churn |
| --- | ---: | ---: |
| RSS | 149.7 MiB | 152.0 MiB |
| user cache | 20.8 MiB | 20.8 MiB |
| post cache | 32.2 MiB | 32.1 MiB |
| negative cache | 6.8 MiB | 6.8 MiB |
| user/post/negative evictions | 10,016 / 16 / 16 | 11,040 / 1,040 / 1,040 |

The 2.25 MiB warmed RSS change is below the declared 64 MiB slope allowance.
Peak RSS was 197.5 MiB. Peak directly estimated live ownership was 84.8 MiB,
leaving a 112.8 MiB process residual (allocator, runtime, and SQLite allocations
that cannot be reliably assigned from RSS). After cache clearing and all
transients, RSS was 197.5 MiB and remained below the 3 GiB recovery threshold.
This macOS run explicitly reported Linux anonymous/file RSS, cgroup, PSI, swap,
and OOM dimensions as unavailable; the scheduled Linux job supplies them.

No new dominant leak was demonstrated after the collector fix. The additional
remediation is therefore generic bounding: byte-weighted caches, O(1) bounded
FIFO eviction rings, smaller bounded ingress/monitor queues, payload admission,
and explicit SQLx/SQLite limits. It is not presented as a newly attributed
component-specific leak.

## Conservative production working set

Startup validates the following count-to-byte envelope before pressure actions
are enabled:

| Owner | Hard bound |
| --- | ---: |
| user cache | 512 MiB and 50,000 entries |
| post cache | 1,024 MiB and 40,000 entries |
| active + expired negative state | 128 MiB and two bounded 20,000-entry LRUs |
| ingress channel | 1,000 × 256 KiB = 250 MiB |
| monitor broadcast ring | 32 × 2 MiB = 64 MiB |
| monitor WebSocket outgoing queue | 16 × 2 MiB = 32 MiB per connected client |
| admitted in-flight payload | 256 MiB |
| SQLite page caches | 4 × 64 MiB = 256 MiB |
| SQLite mmap ceiling | 256 MiB |
| Bluesky coordination | about 2.55 MiB, derived from the landed 150-key / 600-waiter limits |

The validated base application working-set ceiling is 2,751.4 MiB including the
collector and fixed observer window, below the 3,072 MiB recovery threshold. SQLite
`temp_store=memory` is reported but transient temp allocations are not assumed
to equal a page-cache reservation; the 326 MiB gap to recovery and the larger
soft/emergency gaps are reserved for SQLite transients, allocator fragmentation,
and unassigned runtime state. WebSocket clients add at most 32 MiB of queued
records each; the external memory envelope and per-client drop-on-full behavior
remain the aggregate containment for client fan-out.

Selected thresholds for the documented 8 GiB host are recovery 3,072 MiB,
sustained soft pressure 3,584 MiB, emergency 4,608 MiB, systemd `MemoryHigh`
4,864 MiB, and `MemoryMax` 5,120 MiB. The hard service ceiling leaves 3 GiB of
host headroom. Recovery confirmation is 60 seconds and soft-pressure
confirmation is 30 seconds.

## Baseline comparison

The checked-in observational reference records 1,141.2 events/s, zero committed
lag, 400 Bluesky profile API calls, and 100% complete hydration for the same
10,000-event driver before the bounded FIFO cache remediation. The final run
recorded 5,194.2 events/s, zero lag, 400 calls, and 100% complete hydration.
The artifact reports ratios/deltas for all four dimensions. The throughput gain
is primarily removal of the old cache's repeated full-map expiry/oldest scans;
it is not a cross-host benchmark and CI trends should compare like runners.

The acceptance result passed hard-limit, component/count bound, backlog,
checkpoint monotonicity, transient settling, and warmed-slope checks. Pressure
actions and controlled emergency exit remain disabled by default pending the
ordered canary described in `runtime-memory-operations.md`.
